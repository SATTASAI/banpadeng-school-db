# ตั้งค่าผู้อนุมัติ ผู้รับผิดชอบงาน และผู้รับผิดชอบโครงการ — Patch 1.3.1

## ผลลัพธ์

หน้าตั้งค่าที่ `/budget.html?view=roles` แบ่งเป็นหมวดหุบ–ขยาย 3 หมวด: ผู้อนุมัติงาน ผู้รับผิดชอบงาน และผู้รับผิดชอบโครงการ โดยคงการตั้งลายเซ็นเดิมไว้ในหมวดผู้อนุมัติ

ทะเบียนโครงการใช้รายการจริงของทุกฝ่ายและทุกปี ไม่ผูกกับปีที่เลือกในหน้างบประมาณ แต่ละโครงการมีหัวข้อย่อย ค้นหาได้ และแก้ชื่อ ฝ่าย ปี สถานะ รายละเอียด และบัญชีผู้รับผิดชอบได้ ผู้รับผิดชอบหลายคนใช้ `project_owners.user_id` เชื่อม `users.id` ชื่อจึงเปลี่ยนตามบัญชี ไม่ใช้ชื่อที่พิมพ์ลอย ๆ

ครูเห็นทะเบียนโครงการเฉพาะที่รับผิดชอบ ทั้งหน้าฝ่าย ภาพรวม ค้นหา งบประมาณ และไฟล์/ประวัติโครงการ ผู้บริหาร (`executive`) และแอดมิน (`superadmin`) เห็นทั้งหมดตามขอบเขตที่เลือก ผู้ตรวจ/การเงิน/พัสดุยังเปิดและดำเนินการเอกสารที่เกี่ยวข้องกับหน้าที่ผ่านคิวงานได้ โดยไม่เปิดทะเบียนโครงการทั้งหมดให้ครูที่ได้รับหน้าที่นั้น

## ข้อผิดพลาดที่พบและแก้

| ประเด็น | ผลกระทบเดิม | การแก้ไข |
|---|---|---|
| โครงการแสดงกับผู้เข้าสู่ระบบทุกคน | ผู้ไม่รับผิดชอบเห็นชื่อ รายละเอียด ยอด และไฟล์ | บังคับสิทธิ์ฝั่ง API และกรองประวัติไฟล์ด้วย ไม่อาศัยการซ่อนปุ่ม |
| เปลี่ยนเจ้าของโดยลบก่อนเพิ่ม | รายชื่อหายเมื่อเพิ่มบัญชีใหม่ไม่สำเร็จ | ตรวจบัญชีก่อนเขียนและทำ metadata/owners/audit ใน transaction เดียว |
| บัญชีไม่ถูกต้อง/ปิดใช้/รออนุมัติและ ID ซ้ำ | สิทธิ์ผิดหรือบันทึกไม่ได้ | ตรวจสถานะ/บทบาทและลบ ID ซ้ำก่อนบันทึก |
| ยืนยันชื่อซ้ำแล้วแก้ ID ที่ไม่มีจริง | คืนสำเร็จทั้งที่ไม่มีโครงการ | ตรวจโครงการก่อนทุกครั้ง รวม `confirm_duplicate` |
| คิวเจ้าหน้าที่ผูกกับรายการโครงการที่มองเห็น | การจำกัดโครงการจะทำให้เจ้าหน้าที่รับเรื่องไม่ได้ | แยกคิวเอกสารตามหน้าที่จากทะเบียนโครงการ และนับ badge จากงาน/ข้อความ |
| การเงินรับเรื่องแล้วไม่มีแจ้งพัสดุโดยตรง | ผู้รับขั้นถัดไปไม่ทราบงานใหม่ | แจ้งเจ้าหน้าที่พัสดุทั้งสองตำแหน่งพร้อมลิงก์ `/procurement.html?expense=…` |
| เอกสารแนบเพิ่มแจ้งเฉพาะการเงิน | ผู้ตรวจที่กำลังพิจารณาอาจไม่รู้ว่าเพิ่มหลักฐานแล้ว | แจ้งผู้ตรวจสถานะ pending ด้วย เมื่อไฟล์อัปโหลดสำเร็จ ใช้ event เดียวกันกันแจ้งซ้ำ |
| งานพัสดุส่งพร้อมกัน | คำสั่งที่แพ้การเปลี่ยนสถานะยังสร้าง event/audit/แจ้งเตือนได้ | ใช้ revision และ transaction token guard ครอบสถานะ ประวัติและผู้รับแจ้ง รวมขั้นตรวจรับ |
| ทะเบียนหลายปีเกินจำนวน parameter ที่ D1 รองรับ | รายการขนาดใหญ่เปิดไม่ได้ | แบ่งการอ่าน owners/items/docs/signoffs/cases/notifications ชุดละไม่เกิน 80 ID |
| ค้นหา/รีเฟรชหน้าตั้งค่าระหว่างกรอก | แบบร่างยังไม่บันทึกหาย | ซ่อนผลค้นหาแทนสร้างฟอร์มใหม่ และเก็บแบบร่างเมื่อโหลดทะเบียนซ้ำ |
| เปลี่ยนปีหลังมีเอกสาร หรือสั่งลบโครงการมีประวัติ | ยอดข้ามปีผิดหรือชน foreign key | กันเปลี่ยนปีเมื่อมีเอกสาร กันลบยอดผูกพัน/จ่ายแล้ว/ประวัติพัสดุ และลบข้อมูลที่อนุญาตใน transaction |

## การส่งต่องานและแจ้งเตือน

| เหตุการณ์ | ผู้รับขั้นถัดไป |
|---|---|
| ยื่นคำขอ | หัวหน้าฝ่าย / รองผู้ดูแลฝ่ายตามลำดับที่กำหนด หรือการเงินเมื่อข้ามขั้น |
| ผู้ตรวจเห็นชอบ | ผู้ตรวจขั้นถัดไป / การเงิน / ผู้อำนวยการตามสถานะจริง |
| การเงินรับเรื่อง | เจ้าหน้าที่พัสดุ และสถานะให้ผู้ขอ/เจ้าของโครงการ |
| พัสดุเสนอรายงาน / หัวหน้าเห็นชอบ | หัวหน้าเจ้าหน้าที่พัสดุ / ผู้อำนวยการ |
| อนุมัติจัดซื้อจัดจ้าง / ส่งมอบ / ตรวจรับครบ | เจ้าหน้าที่พัสดุและผู้ตรวจรับ / ผู้ตรวจรับ / การเงินและเจ้าของโครงการ |
| ตรวจเอกสารการเงินเสร็จ | หัวหน้าฝ่ายงบประมาณ / รองผู้ดูแล / ผู้อำนวยการตามการตั้งค่า |
| ผู้อำนวยการอนุมัติเบิกจ่าย | การเงิน |
| ส่งคืน / ไม่เห็นชอบ / เบิกจ่ายแล้ว | ผู้ขอและเจ้าของโครงการที่เกี่ยวข้อง |
| อัปโหลดเอกสารประกอบสำเร็จ | การเงินและผู้ตรวจที่กำลังรอพิจารณา |

ใช้กระดิ่งกลางและ feed เดิมของ School Notify พร้อมลิงก์รายการ เหตุการณ์ใหม่ที่บันทึกสำเร็จเรียก dispatch ผ่าน Worker และมี cron เก็บตก การส่งถึงอุปกรณ์ขึ้นกับการเชื่อม Notify และการตั้งค่ารับแจ้งเตือนของบัญชีนั้น ไม่ได้ส่งข้อความทดสอบถึงผู้ใช้จริงระหว่างการพัฒนา

## ผลตรวจสอบ

- `npm test`: 448/449 ผ่าน เหลือข้อผิดพลาดเดิมใน `navigation-catalog`: เมนูบันทึกความดีมีปลายทางซ้ำกับเมนูหลัก ตรวจเทียบโค้ดก่อนแก้พบรายการซ้ำเดียวกัน ส่วน `personnel-center` ผ่านแล้ว
- ทดสอบเพิ่ม/ปรับครอบคลุมสิทธิ์ทุกจุด เปลี่ยนผู้รับผิดชอบและชื่อบัญชี transaction rollback บัญชีผิด รายการเกิน 100 โครงการ คิวหน้าที่เดิม ลำดับผู้รับแจ้ง เอกสารเพิ่ม และการส่งงานพัสดุพร้อมกัน
- ตรวจ DOM หน้าตั้งค่าผ่าน: 3 หมวด รายการทุกปี ค้นหา/รักษาแบบร่าง บันทึกผู้รับผิดชอบ และข้อผิดพลาดเมื่อลบไม่ได้
- Wrangler build dry-run ผ่าน
- Chromium ในสภาพแวดล้อมนี้เปิดไม่ได้ (`socket() Operation not permitted`) จึงยังไม่ยืนยันภาพจริงบนมือถือ/PC ; ไม่ได้ทดสอบ Push บนอุปกรณ์จริง

โครงสร้าง `procurement_cases.action_revision` และ `procurement_action_tokens` สร้างโดย `ensureProcurementSchema` อัตโนมัติเมื่อโมดูลเริ่มทำงาน ไม่ต้องย้ายข้อมูลผู้รับผิดชอบเดิม
